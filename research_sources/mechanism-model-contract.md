# Mechanism demo model contract

Import `{ DEMO_IDS, createState, defaultInputs, stepDemo, describeDemo }` from `mechanism-models.mjs`.

- `DEMO_IDS`: `['fixed-shooter','turret-shooter','piece-handling','elevator-wrist','telescoping-arm','drivetrain','climb-balance']`.
- `defaultInputs(id)` returns a fresh flat object; use its keys and types for controls. Common controls: `enabled`, `request`, `reset`, `sensorValid`, `stale`, `obstructed`. Numeric controls use suffixes `M`, `Rad`, `RadPerSec`, `Mps`.
- `createState(id)` returns a new initial state; no mutations. `stepDemo(id, state, inputs, dt=0.02)` returns a NEW state and never mutates arguments. `describeDemo(id, state, inputs)` returns the readout for that state.
- Description: `{phase: string, reason: string, sensors: [{name, value, unit}], outputs: [{name, value, unit}], activeTrace: string[], gates: [{id,label,ok}], geometry: {kind, x, y, angle, extension, piece}}`. Values are numbers, booleans or short strings; geometry numbers are meters and radians. `piece` is `{x,y,visible}`. `x`, `y`, `angle`, `extension`, and piece coordinates are always present, even where a given mechanism does not use them.
- Active trace IDs are shared: `input`, `sensor`, `condition`, `output`, `motion`. Use them as conceptual stages, not line IDs from real code. `gates` includes `enabled`, `sensor`, `clear`, `armed`, and `homed` where relevant. Each indicates a true/false prerequisite.
- Models are original, intentionally simplified behavioral illustrations, not executions of team source or hardware simulations. Describe their assumptions in the surrounding lesson/UI.
- Disable stops outputs and sets phase `disabled` without creating a fault. After disabling, a held request cannot restart motion; release the request after enabling before issuing a fresh request. Invalid/stale sensor or obstruction stops output and latches a fault. A fault can clear ONLY on an explicit `reset` while the request is released and the fault conditions are clear; a later request is then required. Homing models require the `home` toggle while request is released and conditions are clear. `reset` is a user action, not an automatic restart.

## Model controls
All models share `enabled`, `request`, `reset`, `sensorValid`, `stale`, `obstructed`.
- `fixed-shooter`: `targetRadPerSec`, `pieceDetected`.
- `turret-shooter`: `targetRadPerSec`, `targetAngleRad`, `pieceDetected`.
- `piece-handling`: `frontLeft`, `frontRight`, `backSensor`.
- `elevator-wrist`: `home`, `targetHeightM`, `targetWristRad`.
- `telescoping-arm`: `home`, `targetAngleRad`, `targetExtensionM`.
- `drivetrain`: `vxMps`, `vyMps`, `omegaRadPerSec`.
- `climb-balance`: `home`, `targetHeightM`, `cageDetected`.

`home` represents the operator recording a simulated asserted home switch with the request released, not an automated homing move. Home starts false for elevator, arm and climb.
`geometry.x/y` are field position for drivetrain; others stay zero. `geometry.angle` is turret/shoulder/wrist heading, drivetrain field heading, or fixed-shooter flywheel phase. `geometry.extension` is elevator/climb height or telescoping extension in meters. `geometry.piece.x` is a normalized progress (0 to 1), `piece.y` is zero. Piece-handling sensors are manual scenario inputs, not generated by position. `flywheel velocity`, heading and extension appear in sensors as applicable.

Example: `const p = {...defaultInputs('telescoping-arm'), home:true}; let s = stepDemo('telescoping-arm', createState('telescoping-arm'), p); s = stepDemo('telescoping-arm', s, {...p,home:false,request:true}); const view = describeDemo('telescoping-arm',s,{...p,home:false,request:true});`

The fixed-shooter flywheel uses an exact first-order velocity response while enabled; for the disable teaching state this ideal model stops instantly and freezes the visual phase (not physical coast-down behavior). All other simulated mechanism positions also freeze when disabled.

## Aiming and clearance additions
`fixed-shooter` adds `targetHeadingRad` (default 0). With a request it rotates the chassis at up to 1.5 rad/s along the shortest wrapped heading difference; feed additionally requires heading error ≤ 0.05 rad. The existing `geometry.angle` remains flywheel phase; `geometry.chassisHeadingRad` and `geometry.flywheelAngleRad` are explicitly present for all models. `sensors` adds `Chassis heading` for fixed and `Turret angle` for turret; `outputs` adds `turnRadPerSec`.

`turret-shooter` has an educational hard-stop envelope [-2.6, +2.6] rad. It considers equivalent targets separated by 2π and travels directly to the nearest equivalent within the envelope without wrapping through a hard stop. If no equivalent exists, phase `unreachable`, gate ID `limit` is false, and turn/feed stop. This guard and envelope are original teaching assumptions, not claims about a specific robot implementation.

After a shooter feeds one modeled piece, phase `spent` explains that the simulated piece sensor must first be cleared (`pieceDetected:false` for a step) before another piece can be fed. It does not automatically reload on request release.

`elevator-wrist` adds an original educational clearance sequence: wrist targets above 0.2 rad require a height goal ≥0.3 m. The elevator first raises to 0.3 m before crossing the wrist limit; it first stows the wrist to 0.2 rad before lowering below 0.3 m. An incompatible low-height/extended-wrist goal stops both and yields phase `incompatible`. Gates `compatible` and `clearance` explain the sequence. This is not a sourced robot safety envelope.

`drivetrain` adds boolean `differential` (default `false`, the swerve-like holonomic model). When true, the model discards robot-relative `vyMps` but preserves `vxMps` and `omegaRadPerSec`; its `lateral` gate and reason explain that nonholonomic constraint. Sensors include `Drive kind` (`swerve` or `differential`), and `geometry.differential` is true for the differential mode. This simple kinematic illustration does not model slip, wheel limits, motor dynamics, or source-code execution.

Both shooter descriptions include the existing simulated flywheel velocity in rad/s and an additional `Flywheel velocity (source RPS)` sensor in RPS, calculated as rad/s ÷ 2π. Elevator-wrist adds `Height (source comparison)` in inches, calculated as simulated meters ÷ 0.0254. These are paired unit representations of the same simulated state, not measurements from the cited robot.

## Numerical assumptions and limits

These are original teaching constants, not measured or team-sourced robot specifications. The shooter uses an exact constant-target first-order speed response with a 0.4 s time constant and a 4% speed-readiness band. Disabling freezes motion and stops the ideal flywheel instantly; it does not model physical coast-down. Chassis heading changes at at most 1.5 rad/s. The turret has illustrative travel limits of −2.6 to +2.6 rad and selects a reachable equivalent angle without passing through those stops.

The elevator height is bounded to 0–1.5 m, with a 0.5 m/s rate and a wrist rate of 1 rad/s. Its illustrative coordination thresholds are 0.3 m height and 0.2 rad wrist angle. The telescoping arm uses shoulder travel of −1 to +1.4 rad, extension 0–1 m, rates of 0.8 rad/s and 0.35 m/s, and a 0.1 rad alignment band. These constraints are examples, not engineering-approved collision envelopes. Recording a simulated home event is not an automatic homing movement.

The drivetrain integrates a constant robot-relative planar twist over each step; the differential mode discards lateral velocity. It omits module dynamics, tire contact, slip and localization error. The climber uses a bounded, 0.25 m/s height change after simulated home and cage conditions. It models neither engagement, load support nor charge-station balance.

Piece and contact sensor booleans are independent scenario inputs, not sensor values generated from the drawn geometry. Students can intentionally supply an inconsistent or stale observation. Source-specific annotations in mechanism-sources.json describe the actual Java excerpt; the model's generic flow stages are separate and must not be presented as executed Java lines.
